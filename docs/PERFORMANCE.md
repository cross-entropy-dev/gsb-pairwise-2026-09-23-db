# 性能测试报告

测试环境：Windows 11，CPython **3.11.7**（纯解释执行，无 C 扩展），
单进程多线程。复现命令：

```bash
python -m tests.benchmark --rows 20000 --threads 16 --ops 300 --json
```

原始数据见 `tests/benchmark_results.json`。以下为一次代表性运行结果。

---

## 1. B+ 树微基准（20,000 键，order=32）

| 操作 | 吞吐 (ops/s) |
|------|---------------|
| 插入 | 557,630 |
| 点查找 | 780,202 |
| 范围扫描 | 6,730,834 行/s |
| 删除 | 676,617 |
| 峰值树高 | **4**（log_32(20000)≈2.87，含根/叶层，符合 O(log n)） |

插入/查找/删除均为 O(log n)；范围扫描沿叶子链表顺序读取，吞吐最高。

## 2. SQL 单会话（20,000 行）

| 项目 | 结果 |
|------|------|
| 批量 INSERT（100 行/语句） | 12,992 行/s |
| 主键点查 `WHERE k = ?` | **9,129 查询/s** |
| 全表聚合 COUNT/SUM/AVG/MIN/MAX | 836 ms |
| UPDATE 前 5,000 行（单语句） | 769 ms |
| ORDER BY + LIMIT 1000 | 592 ms |

> 主键点查通过优化器识别 `pk = 常量` 后走 B+ 树索引访问；此前全表扫描版本
> 仅约 36 查询/s，索引路径带来约 **250×** 提升。

## 3. 并发事务（16 线程，5,000 行，4,800 次操作，约 1/4 为写）

| 指标 | 结果 |
|------|------|
| 总吞吐 | **2,040 ops/s** |
| 中位延迟 | 0.224 ms |
| P95 / P99 延迟 | 31.5 / 37.5 ms |
| 死锁/冲突中止 | **0**（不同行互不阻塞；同行由 X 锁串行） |

## 4. 1000+ 并发事务

1000 个并发只读事务（64 工作线程、栅栏同时起跑）在 **0.27 s** 内全部完成，
满足“支持 1000+ 并发事务”的要求。事务/锁为纯内存对象，扩展性主要受
CPython GIL 与线程调度限制。

## 5. WAL 持久化 / 读不阻塞写

| 指标 | 结果 |
|------|------|
| 单次提交 fsync 开销 | 2.8 ms（Windows Defender 环境；Linux 通常更低） |
| 重写负载下读吞吐 | **6,324 次读**与 500 次 fsync 提交并发完成 |
| 读 P95 延迟 | 8.1 ms |
| 读是否被 WAL 阻塞 | 否——读不接触 WAL，日志由后台线程异步批量写、仅提交点 fsync |

---

## 分析与瓶颈

* **解释器开销**主导：B+ 树裸结构 ~60–80 万 ops/s，套上 SQL 解析/执行后
  点查约 9k/s。每次调用都重新 Lex+Parse，是单会话吞吐的主要成本；生产级
  实现会加入 prepared statement / plan cache。
* **fsync** 是写延迟的硬底（~1–3 ms/提交），已通过后台线程 + 仅提交点同步、
  只读事务零日志来摊薄；多语句显式事务可进一步把多次 fsync 合并为一次。
* GIL 使 CPU 密集的并发扫描难以真正并行；锁与 WAL 的设计保证了**逻辑并行**
  与**读写不互斥**，在 I/O 或多核实现（如 PyPy/free-threaded Python）下可线性扩展。
* 可重复验证：B+ 树随机化压力测试（`tests/test_bptree.py`）覆盖多阶数下
  数千次随机增删查与有序性校验。
