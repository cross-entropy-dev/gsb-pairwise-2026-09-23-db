# minidb 架构设计文档

一个从零实现的、支持 ACID 事务的内存数据库引擎。纯 Python 3.10+ 标准库实现，
不依赖任何第三方数据库库。

---

## 1. 总体架构

```
                          ┌──────────────────────────────┐
                          │            CLI               │  minidb/cli.py
                          └──────────────┬───────────────┘
                                         │ SQL 文本
                          ┌──────────────▼───────────────┐
                          │           Session            │  事务边界/自动提交
                          └──────────────┬───────────────┘
        SQL 子集                          │ AST
 ┌───────────────────────────────────────────────────────────────┐
 │  sql/lexer.py   词法分析  SQL → Token 流                        │
 │  sql/parser.py  递归下降  Token → AST（sql/ast.py）             │
 └───────────────────────────────┬───────────────────────────────┘
                                 │ AST
 ┌───────────────────────────────▼───────────────────────────────┐
 │  engine/planner.py   基于规则的优化（谓词下推 / 主键点查识别）   │
 │  engine/executor.py  扫描 / 嵌套循环连接 / 哈希聚合 / 子查询     │
 │  engine/expressions.py  表达式求值（SQL 三值逻辑 / LIKE / 关联） │
 └───────────────────────────────┬───────────────────────────────┘
                                 │
 ┌───────────────────────────────▼───────────────────────────────┐
 │  txn/manager.py  事务 ID、MVCC 快照、提交/中止、可见性          │
 │  txn/locks.py    行锁/表锁(IS/IX/S/X)、死锁检测、锁升级         │
 │  txn/wal.py      后台 WAL 线程 + fsync，崩溃恢复重放            │
 └───────────────────────────────┬───────────────────────────────┘
                                 │
 ┌───────────────────────────────▼───────────────────────────────┐
 │  storage/bptree.py   内存 B+ 树（O(log n)，叶子链表）           │
 │  storage/table.py    多版本表（每个键一条版本链）               │
 │  storage/schema.py   类型系统与约束（INT/FLOAT/VARCHAR/...）     │
 └───────────────────────────────────────────────────────────────┘
```

模块划分（与交付要求一一对应）：

| 要求         | 文件                                    |
|--------------|-----------------------------------------|
| lexer        | `minidb/sql/lexer.py`                   |
| parser       | `minidb/sql/parser.py`、`minidb/sql/ast.py` |
| executor     | `minidb/engine/executor.py`、`expressions.py`、`planner.py` |
| storage      | `minidb/storage/bptree.py`、`table.py`、`schema.py` |
| transaction  | `minidb/txn/manager.py`、`locks.py`、`wal.py` |

## 2. 存储引擎

### 2.1 B+ 树（`storage/bptree.py`）

* 经典 B+ 树，阶（order）可配（默认 32）。内部节点最多 `order` 个键、
  `order+1` 个孩子；叶子最多 `order` 条记录。
* **叶子节点通过 `next` 指针串成有序链表**，全表扫描与范围扫描沿链表进行，
  无需回溯到内部节点。
* 查找：从根到叶 O(log n)，叶内二分定位；插入超限时叶子/内部节点一分为二，
  提升键上溯，必要时生长新根。
* 删除不主动合并（in-memory 场景下重平衡收益低），仅在内部根变空时坍缩一层；
  深度始终保持 O(log n)。
* 泛型键类型（int / str / tuple 均可比较即可）。

### 2.2 多版本表（`storage/table.py`）

* 每张表是一棵 `BPlusTree[key, list[Version]]`。
* 每个键对应一条**版本链**，版本结构：

  ```
  Version { row: tuple, xmin: txid, xmax: txid }
                    │              │
                    创建者事务     删除/覆写者事务（0 = 仍存活）
  ```

* 无用户主键的表使用单调递增的代理键 `rowid`（分配由行内锁保护）。
* 后台 GC 线程周期性回收“所有现存事务都不可能再看到”的死版本（见 §5）。

### 2.3 类型系统（`storage/schema.py`）

`INT / FLOAT / VARCHAR(n) / TEXT / BOOLEAN`。写入时统一校验并强转为原生
Python 类型；`NOT NULL`、`VARCHAR` 长度、主键非空均在此强制。SQL 布尔字面量
`TRUE/FALSE`、数字字符串等按 SQL 语义转换。

## 3. SQL 层

### 3.1 词法分析（Lexer）

手写有限扫描器，产出 `Token(kind, value, literal)`：关键字（大写归一）、
标识符（保留原大小写，比较时忽略大小写）、整数/浮点、单引号字符串（`''`
转义）、双引号引用标识符、比较运算符（`<>` 归一为 `!=`）、行/块注释。

### 3.2 语法分析（Parser）

手写**递归下降**，运算符优先级（低→高）：

```
OR → AND → NOT → 比较(= <> < <= > >= / LIKE / IS [NOT] NULL / IN / BETWEEN)
   → 加减 → 乘除 → 一元(+ -) → 基本项(字面量/列/函数/括号/子查询)
```

支持：`CREATE TABLE`（含表级 `PRIMARY KEY`）、多行 `INSERT`、`UPDATE`、
`DELETE`、`SELECT`（`WHERE / GROUP BY / HAVING / ORDER BY / LIMIT / OFFSET /
DISTINCT`）、`INNER/LEFT JOIN`、标量子查询、`IN (subquery)`、聚合函数、
事务控制语句与 `SHOW TABLES / DESCRIBE / EXPLAIN`。

### 3.3 查询优化器（`engine/planner.py`）

基于规则，当前实现两类改写：

1. **谓词下推**：把顶层 `AND` 合取项中只引用单表列的谓词下推到该表扫描阶段，
   不满足条件的行根本不进入连接管线；跨表谓词、含子查询的谓词保留在连接后的
   过滤阶段。LEFT JOIN 的右侧保留表不下推，避免外连接被错误地变成内连接。
2. **主键点查识别**：扫描/更新/删除时，若谓词含 `pk = 常量`，直接走 B+ 树
   点查 `O(log n)`，而非全表扫描 O(n)。

`EXPLAIN` 输出可读执行计划（哪些谓词被下推、连接顺序、分组/排序/限制）。

### 3.4 执行器（`engine/executor.py`）

* 连接：**嵌套循环连接**，单表谓词在扫描时即应用；LEFT JOIN 未匹配侧补 NULL 行。
* 聚合：`GROUP BY` 用哈希分组；`COUNT/SUM/AVG/MIN/MAX`，支持 `DISTINCT`、
  `COUNT(*)`、`HAVING`；无 GROUP BY 时做标量聚合（空集上 COUNT=0，其余为 NULL）。
* 排序：多键稳定排序，支持每列独立 ASC/DESC 与序号排序；NULL 规则
  ASC 末尾 / DESC 开头；异构类型回退为字符串序。
* 子查询：共享外层语句快照；通过 contextvar 维护外层作用域栈以支持**关联子查询**。
* 表达式：实现 SQL **三值逻辑**（TRUE/FALSE/UNKNOWN），`NULL` 参与运算与比较
  的传播、`AND/OR` 的短路真值表、`LIKE`（`%`/`_`）。

## 4. 事务与并发控制

### 4.1 MVCC 快照可见性（`txn/manager.py`）

每个事务获得单调递增 `txid`。快照冻结：

* `taken_at`：快照时的下一个事务号；
* `active`：当时仍在运行的事务集合；
* `status_fn`：查询某事务最终提交/中止状态。

版本可见规则（PostgreSQL 风格）：

```
版本可见 ⇔ 创建它的事务在快照前已提交
         ∧ 删除它的事务在快照时未提交
         ∧ （创建者是自己，或删除者是自己时按自身写可见处理）
```

* **READ COMMITTED**：每条语句取新快照（能看到语句开始前已提交的数据）。
* **SERIALIZABLE**：首次读时固定快照（事务内可重复读），并在所有被读表上
  取表级 **S 锁（S2PL，严格两阶段封锁）**，从而杜绝幻读并保证冲突可串行化。
  S 锁在获取之后才固定快照，保证“等待写者完成的读者”能读到其已提交结果。

### 4.2 封锁（`txn/locks.py`）

* 行锁 `S/X`，表锁意向锁 `IS/IX` 加 `S/X`，标准意向锁相容矩阵。
* 写者：先取表 `IX`，再对命中行取 `X`；不同行的写者互不阻塞。
* SERIALIZABLE 读者取表 `S`，与 `IX/X` 互斥。
* 锁获取统一遵循“全局元锁 → 资源条件变量”的加锁顺序，避免管理器自锁；
  等待时支持超时与虚假唤醒。

### 4.3 死锁检测

每次等待前构建**等待图**（waiter → 它正在等待的所有锁持有者），DFS 检测环。
一旦成环，选择环中**最年轻（txid 最大）的事务作为牺牲者**抛出
`DeadlockError`，由上层回滚，打破循环等待。

### 4.4 锁升级（行锁 → 表锁）

单事务在一张表上持有的行锁数达到阈值（默认 100）时：释放其该行上的全部行锁，
升级为表级 `X` 锁（若暂不满足则后续访问走表 X 的阻塞获取路径）。以固定的少量
表锁替代大量行锁，控制锁表内存与管理开销。

### 4.5 写流程（防丢失更新）

UPDATE/DELETE：

1. 语句快照下扫描出候选键；
2. 按**全局稳定顺序**对候选键加 X 锁（避免加锁顺序导致的 AB-BA 死锁）；
3. READ COMMITTED 下加锁完成后**再取一次快照**，对等待期间被他人提交的行
   重新判定谓词后再改——配合行 X 锁消除丢失更新；SERIALIZABLE 沿用固定快照
   （表 S 锁已排除幻读/并发写）；
4. 每个物理变更“先写 WAL，再改 B+ 树”。

中止无需 UNDO：新版本带着中止事务的 xmin，对任何事务都不可见，随后由 GC 回收。

## 5. 持久化与崩溃恢复（`txn/wal.py`、`engine/database.py`）

### 5.1 WAL

* JSON Lines，每条记录一行：`begin/create/insert/update/delete/commit/abort`。
* 专用**后台 WAL 线程**独占文件句柄，变更通过队列投递；`commit` 请求携带事件，
  仅在 `write + flush + fsync` 全部完成后才置位。因此：
  * **读操作完全不接触 WAL**，日志写入不阻塞读；
  * 事务只有在 commit 记录落盘后才对外可见（崩溃安全）。
* BEGIN 记录**惰性写入**：事务首次发生变更时才写，故只读事务从不清刷日志。
* 打开日志时自动**截断残缺的尾部半行**（torn write），防止后续 append 与其
  拼成一行而损坏。

### 5.2 恢复

启动时：

1. 若存在 `checkpoint.json`（上次干净关闭写出），载入其中的表结构与存活行；
2. 重放 `wal.log`：只有**带有 commit 记录的事务**的数据记录会被重放；
   缺少 commit（崩溃在事务进行中）或带 abort 的事务一律丢弃——这正是崩溃后
   原子性的来源；
3. 推进事务号计数器到重放的最大 txid 之后。

干净关闭（CLI `.quit`、`db.shutdown()`）会先中止残余事务、做一次 GC，再把
一致快照原子落盘（临时文件 + `os.replace`）并截断 WAL。

### 5.3 MVCC GC

后台线程按“最老活跃事务”水位回收：由已结束且所有人都越过的事务创建/删除的
版本被清除；版本链清空时删除键。检查点前也会强制做一次 GC。

## 6. ACID 对照

| 特性 | 实现手段 |
|------|----------|
| Atomicity | 每条语句同事务；WAL 仅重放已提交事务；失败即整体回滚（版本不可见 + 放锁） |
| Consistency | 类型/NOT NULL/主键唯一/长度约束在写入时强制；序列化隔离防止异常交错 |
| Isolation | MVCC 快照（RC 逐语句、SERIALIZABLE 固定快照 + S2PL 表 S 锁） |
| Durability | 提交记录 fsync 后才可见；WAL 重放 + 检查点；崩溃/残缺日志可恢复 |

---

## 7. 关键并发不变量

* 读不阻塞写、写不阻塞读（MVCC 快照读）；写写同行用 X 锁串行化。
* 多行写按全局键序加锁；等待图成环即牺牲最年轻事务。
* 物理变更先日志后内存；提交先 fsync 后可见。
* 检查点只在无活跃事务时进行，保证快照一致。

---

## 8. 局限与可扩展方向

* 连接为嵌套循环、谓词下推为单表级别；可加入哈希/排序合并连接与代价模型。
* 仅单列主键被自动索引；可扩展二级索引与复合主键。
* SERIALIZABLE 采用 S2PL 表锁（强但并发度低于真正的 SSI）；可演进为
  基于读写冲突检测的可串行化快照隔离。
* 检查点为全量快照；可改为增量/模糊检查点。
